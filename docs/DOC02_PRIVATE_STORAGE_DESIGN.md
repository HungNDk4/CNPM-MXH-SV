# DOC-02 — Private PDF storage & access engineering baseline

**Project:** Mini Study Network · **Phase:** implementation design for DOC-03/04 · **Date:** 2026-10-21
**Approved product constraints:** ADR-011 guest active/free PDF metadata, login for bytes; ADR-012 exactly 1 PDF, 1..10,485,760 bytes; ADR-013 active after safe persistence, admin hides after publish; ADR-014 low-cost; ADR-015 publicly reachable HTTPS without students' laptops.

## 1. Selected implementation strategy (vendor-neutral)

Use a server-owned **private filesystem adapter** for initial development/testing. Object names are random UUIDs generated by server, stored outside public `/uploads`, with `DOCUMENT_PRIVATE_DIR` as the exclusive storage root. Filesystem permissions are restricted; no static route, raw key, original pathname, or public signed URL is serialized. App runs with minimal filesystem privileges. No original filename ever controls the storage path.

This is a **testable implementation baseline, not the final hosting/provider selection**. For production, an always-on backend with a truly persistent mounted volume (and backup/restore) is required. Ephemeral serverless Functions/Vercel filesystem **must not** use this adapter to persist PDF files. Hosting/provider/operational cost and durable volume are still OPEN; a managed private blob adapter can be added after an isolated PoC and explicit approval. Do not enable uploads on a host with nonpersistent storage.

## 2. Data/migration

Add separate `document_files` table (FK `post_id` UNIQUE -> `posts.id`, on-delete cascade), containing opaque `storage_key`, original sanitized filename, MIME `application/pdf`, size, SHA-256, created_at. This table is private and **must never** be returned in SafePost. No migration of legacy `posts.file_url` — such data stays unavailable under SEC-01; manual reviewed backfill is a separate task. No automatic `sequelize.sync({ alter:true })` in production. Apply explicit migration before enabling new document routes.

Existing `posts` row is created at `status=active` **only within the same DB transaction** as `document_files` metadata. Storage write happens first; if DB insert/commit fails, remove the newly stored blob. Metadata and post become visible only after transaction commit. Protect access by rechecking post status and price on every download. SQL rollback cannot revert disk writes by itself: compensation deletes the object; reconciliation/periodic orphan audit remains operational follow-up.

## 3. HTTP flow

`POST /api/documents` (student Bearer) accepts `multipart/form-data`: exactly one field `file` (PDF), required `title`, optional `description`, `subject`, `tags`; create 201 + SafePost. Guest 401. Reject absent/multiple files, incorrect extension+MIME+PDF magic/trailer, empty contents, oversize, oversized fields/parts; clean all temp/orphans. No "public file_url" upload or URL-only fallback. Reject legacy paid creation paths.

`GET /api/posts?type=document` and `GET /api/posts/:id` expose only safe metadata of active/free PDFs to guests, as secured in SEC-01. Ordinary guest general feed remains 401 (ADR-002 OPEN).

`GET /api/documents/:postId/download` (active-user Bearer required) checks an **active**, free, `document` post and metadata, opens only an opaque storage key, returns 200 `application/pdf` with `Content-Disposition: attachment`, `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`; no raw/signed URLs or redirect. Hidden/deleted/paid/missing PDF -> 404, unauthenticated ->401. Any active student may download any active/free PDF. `/uploads` remains unmounted.

**Retention:** Soft-deleted document bytes remain in private storage but cannot be fetched via API. Deletion retention/physical purge is **OPEN**: do not silently invent a purge window. Manual/periodic orphan inventory before cloud rollout is required.

## 4. Upload parser/security

**Prerequisite:** SEC-04 patched Multer 2.4.0 PR #24; never enable on Multer 1.x. Bounded size <=10 MiB inclusive; `memoryStorage` is a local test adapter tradeoff (one max-sized PDF held briefly in memory), with strict file/field count and request-rate limits. For exposed production deployments, memory/concurrency quotas and pressure tests required; proxy max body must permit multipart overhead. Format checks on extension/MIME and PDF header/trailer are **not full malware scanning**. PDF content security scan/CDR, malware policies, per-user quota, backup/restore, and moderation UX remain separate pending release criteria. No untrusted upload path, filename or header may control filesystem paths.

## 5. Verification

CI disposable MySQL: create two unique users, upload synthetic minimal PDF, check 201 and private DB row, guest safe metadata, guest/invalid token download 401, another student authenticated download 200 attachment, hidden/deleted/paid 404, direct static 404, duplicate/missing/non-PDF/empty/oversize file 4xx, cross-user edit/delete 403, cleanup files and DB fixtures. No real copyrighted/student PDF in repository.

**Gate levels:** DOC-02 design = ready for scoped local implementation; DOC-03/04 = implemented only when CI runtime tests pass. **Public production deployment = blocked** until actual persistent host/volume/cloud PoC and operational/security acceptance. No provider, billable account, deployment, or automatic overage authorized here.
